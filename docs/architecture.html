Agent + RAG + MCP

An interactive walkthrough of how an autonomous ReAct agent, a Chroma-backed retrieval system, and a FastAPI tool server work together — built on Ollama (gemma4:e4b), entirely on your machine.

Explain It Simply 🙂

No coding knowledge needed. Here's what's actually happening, in plain English, with everyday analogies.

The Big Picture

This project builds a smart assistant that can answer questions, do math, manage files, and search through your documents — and it does all of this on your own computer, without sending anything to the internet or needing a paid subscription. There are three "departments" working together: the Agent (the brain that decides what to do), RAG (the library it can search for facts), and the MCP Server (a reception desk that lets other programs use the same tools over a network).

📚 1. RAG — Building the Library

Imagine a stack of notes you want your assistant to instantly search through.

1
Gather the notes▸

The system looks in a folder and picks up every note file it finds. Right now there are two: one about trading strategies, one about workplace automation.

2
Cut the notes into small index cards▸

A long document is hard to search effectively, so each file is sliced into bite-sized chunks (roughly a short paragraph each), with a little overlap between chunks so no sentence gets awkwardly cut in half and loses its meaning.

3
Translate each chunk into "meaning numbers"▸

A small AI model (running locally, no internet needed) reads each chunk and converts its meaning into a list of numbers. Chunks about similar topics end up with similar numbers — even if they use completely different words. This is what lets you search by meaning instead of just exact keyword matching.

4
File everything away▸

All those number-translations get saved into a small local database (Chroma), stored on disk. Think of it as a card catalog organized by meaning instead of alphabetically.

5
Search▸

When someone later asks "what's my straddle strategy?", that question is also translated into numbers, and the system finds the 3 chunks whose numbers are "closest" in meaning — even if exact words don't match. It returns those chunks plus a confidence score and which file they came from.

🤖 2. The Agent — The Decision-Maker

This is the part you actually talk to. It uses "Reason + Act" — think of someone thinking out loud before doing each step.

1
You ask a question▸

E.g. "What is 15% of 2500?"

2
It thinks▸

The local AI model reads your question and reasons: "I need to do a calculation here."

3
It picks a tool▸

Rather than trying to do math "in its head" (AI models are often bad at that), it decides to use a calculator tool, and writes down exactly what to calculate: 2500 × 0.15.

4
The tool actually runs▸

A real, reliable piece of code (not the AI) performs the calculation and gets the exact answer: 375.0. This is called an "Observation" — what actually happened.

5
It checks itself and answers▸

The AI looks at the observation, decides it has enough information, and gives you the final answer: "15% of 2500 is 375." If the task needs more than one step, it repeats this loop (up to 5 times), building on each previous result — like a person crossing off items on a checklist.

🔌 3. MCP Server — The Reception Desk

This part lets the same 5 tools be used by other programs — not just by talking to the AI assistant. It's like opening a phone line so anyone (another app, a script, a website) can call up and say "please run the calculator tool with these numbers" and get an answer back, without needing to involve the AI at all. It runs as a small web service on your computer with four "phone extensions":

❤️

"Are you alive?"

Quick check to confirm the server is running.

📋

"What can you do?"

Lists all 5 available tools and what input each needs.

☎️

"Please do this one thing"

Send a tool name + details, get the result back.

📑

"Please do this whole list"

Same as above, but for several tasks in one request.

If you ask for a tool that doesn't exist, or something goes wrong, it doesn't crash — it just politely reports back that something failed, with an explanation.

🧪 4. Test Client — The Quality Inspector

This is a script whose only job is to double-check that the reception desk (MCP server) is actually working correctly. It runs 7 automatic checks: is the server alive, does it list all 5 tools correctly, does the calculator give the right answer, does "get the time" return something sensible, can it write a file and read it back correctly, does searching the knowledge base return real results, and can it handle a batch of multiple requests at once. If all 7 pass, you see ✓ All tests passed — confirmation everything is wired together correctly before you trust it with real use.

How It All Fits Together

You type a question
        ↓
   The Agent thinks about it
        ↓
   It picks the right tool (calculator, file, time, or search)
        ↓
   The tool runs and gets a real result
        ↓
   The Agent reads that result and gives you a final answer

Meanwhile, the MCP Server offers a side door so other software can use those same 5 tools directly over the network, and the Test Client is the safety check that makes sure that side door works properly. Everything — the AI model, the document search, the tool execution — runs locally on your machine. Nothing is sent to a cloud service, and no API key or subscription is required.

RAG Pipeline rag.py

How raw markdown becomes searchable knowledge. Click each step to expand.
1
Load markdown files from data/docs/▸

DirectoryLoader scans data/docs/*.md (currently trading.md and workfront.md) and reads each file as a TextLoader document with UTF-8 encoding.

loader = DirectoryLoader(docs_path, glob="*.md", loader_cls=TextLoader)
docs = loader.load()
Input: .md filesOutput: LangChain Document objects
2
Chunk text into overlapping windows▸

RecursiveCharacterTextSplitter breaks each document into 500-character chunks with 50-character overlap, so context isn't lost at chunk boundaries.

splitter = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)
chunks = splitter.split_documents(docs)
CHUNK_SIZE = 500CHUNK_OVERLAP = 50
3
Embed each chunk locally▸

Each text chunk is converted into a vector using HuggingFaceEmbeddings with the all-MiniLM-L6-v2 model — runs fully offline, no API calls or keys required.

Model: all-MiniLM-L6-v2384-dim vectors
4
Persist vectors to Chroma DB▸

Vectors + chunk text + source metadata are stored in a local Chroma collection, written to disk at data/chroma_db/ so the index survives restarts.

self.vectorstore = Chroma.from_documents(
    documents=chunks, embedding=self.embeddings,
    persist_directory=self.persist_dir)
self.vectorstore.persist()
5
Similarity search at query time▸

When a query comes in (from the agent's search_rag tool or directly), similarity_search_with_score returns the top-k (default 3) closest chunks by vector distance, each with content, source file, and similarity score.

rag.search("long straddle strategy", k=3)
# → [{content, source, score}, ...]

Agent — ReAct Loop agent.py

Thought → Action → Observation, repeated until the agent has a final answer (max 5 iterations).
1
User submits a question▸

Either typed at the interactive You: prompt, or one of 3 built-in example tasks run automatically on startup.

e.g. "What is 15% of 2500?"
2
LLM reasons: Thought▸

The ReAct prompt template feeds the question plus tool descriptions to gemma4:e4b via Ollama (temperature 0.1). The model emits a Thought: explaining what to do next.

3
LLM picks a tool: Action / Action Input▸

Model outputs Action: <tool_name> and Action Input: <args>, selecting from the 5 registered tools.

4
Tool executes → Observation▸

LangChain's AgentExecutor calls the matching Python function, captures its return value as the Observation, and feeds it back into the prompt for the next reasoning step.

5
Loop or finish: Final Answer▸

Steps 2–4 repeat (up to max_iterations=5) until the model is confident enough to emit Final Answer:, which is returned to the user. Parsing errors are caught via handle_parsing_errors=True.

RAG System — Implementation Details
rag.py · class RAGSystem
Constructor: lazy vs eager load

__init__ checks if persist_dir is non-empty on disk. If yes, it loads an existing Chroma collection — fast path, no embedding inference needed. If not, it defers to load_documents(). This means import-time cost is cheap (just instantiates the embeddings model handle), and you don't pay inference cost until you either load documents or run a search. 

if os.path.exists(persist_dir) and os.listdir(persist_dir):
    # Warm path: attach to existing collection
    self.vectorstore = Chroma(persist_directory=persist_dir, embedding_function=self.embeddings)
else:
    # Cold path: vectorstore stays None until load_documents() is called
    self.vectorstore = None
Text splitter: RecursiveCharacterTextSplitter

Uses RecursiveCharacterTextSplitter rather than the simpler CharacterTextSplitter. The recursive variant tries to split on progressively smaller boundaries: \n\n → \n → " " → character. This means it respects paragraph and line structure before falling back to hard character splitting — important for markdown where semantic units follow newline conventions.

✓ Chosen: RecursiveCharacterTextSplitter

Split order: double-newline → newline → space → char. Preserves markdown paragraph structure. 50-char overlap retains sentence context across chunk boundaries.

✗ Not used: CharacterTextSplitter

Splits strictly on a single separator. Would produce more fragmented chunks for markdown, losing heading-to-body relationships.

Embedding model: all-MiniLM-L6-v2
Dimensions : 384
Parameters : ~22M
Inference  : CPU, ~50ms/chunk on Apple M-series
License    : Apache 2.0
Source     : sentence-transformers / HuggingFace Hub (cached to ~/.cache after first run)
Why this model over larger alternatives?

It's the standard "good enough for semantic similarity with near-zero operational overhead" choice. At 384-d it's faster than all-mpnet-base-v2 (768-d) while trading minimal recall. For a POC with <100 chunks, retrieval quality difference is negligible. The full sentence-transformers download is ~90 MB; once cached it's offline-only.

Chroma storage internals

Chroma 0.4.x uses DuckDB + Parquet under the hood for the persistent backend when you pass persist_directory. Each collection stores embeddings as columnar Parquet files and metadata in a SQLite-like DuckDB layer. The call to .persist() flushes in-memory state to disk — in Chroma ≥ 0.4, writes are also flushed automatically on collection close, so .persist() is technically redundant but harmless.

Similarity search: distance metric

similarity_search_with_score returns L2 (Euclidean) distance by default in Chroma, not cosine similarity. Lower score = closer match. The scores returned are therefore not bounded to [0,1] — a score of 0.3 might be very good, while 1.5+ means poor match. To switch to cosine, pass collection_metadata={"hnsw:space": "cosine"} to Chroma.from_documents().

⚠ Gotcha: score interpretation

The score field in search results is L2 distance, not a similarity percentage. Don't display it to users as a "confidence %" without normalisation. A common filter pattern: discard any result where score > threshold (e.g., 1.2) to avoid returning irrelevant chunks when no good match exists.

Agent — ReAct Implementation Details
agent.py · build_agent() · AgentExecutor
create_react_agent vs legacy initialize_agent

✓ Chosen: create_react_agent (LCEL)

Returns an LCEL Runnable. Composable via | pipe syntax. Explicit prompt template passed in — full control over the ReAct format string. Works with AgentExecutor wrapper for iteration control.

✗ Not used: initialize_agent

Legacy API, deprecated in LangChain 0.1.x. Hides the prompt template internally. Harder to customise the Thought/Action/Observation format for non-OpenAI models like Ollama.

ReAct prompt template — design choices
Question: {input}
Thought:{agent_scratchpad}

# {agent_scratchpad} is the running transcript of prior Thought/Action/Observation turns.
# LangChain appends each loop's output here before the next LLM call.
# The template deliberately omits a trailing space after "Thought:" to avoid
# some models producing a leading newline before their first thought token.
Why a custom template instead of the built-in hub prompt?

The standard hwchase17/react hub prompt is tuned for GPT-4 and includes more verbose formatting instructions that confuse smaller models like gemma4. The simplified template here gives the model fewer structural constraints to satisfy, reducing parse failures — which is why handle_parsing_errors=True is still needed but fires less often.

AgentExecutor configuration
AgentExecutor(
    agent=agent,          # LCEL Runnable: prompt | llm | output_parser
    tools=TOOLS,          # passed separately so executor can route by tool name
    verbose=True,         # logs each Thought/Action/Obs to stderr
    max_iterations=5,     # hard cap prevents infinite loops on parse failures
    handle_parsing_errors=True  # feeds malformed LLM output back as "Invalid output:" observation
)
Ollama LLM: temperature 0.1
Why temperature=0.1 and not 0.0?

Pure greedy decoding (temp=0) makes the model overly repetitive when it gets stuck in a parsing loop — it will reproduce the same malformed output verbatim on every retry. A small temperature (0.1) introduces just enough token variance to escape stuck states while keeping outputs deterministic enough for tool argument parsing. For production use, 0.0 + explicit retry logic is cleaner.

Tool input contract: the single-string constraint

LangChain's Tool class passes all tool input as a single string to func — there's no structured dict dispatch at this abstraction layer. This is why write_file uses the ||| delimiter hack to encode two arguments in one string. 

# The LLM generates:  Action Input: output.txt|||Hello World
# Tool receives:       args = "output.txt|||Hello World"
# Tool parses:         path, content = args.split("|||", 1)

# Alternative: use StructuredTool from langchain.tools which accepts
# a TypedDict or Pydantic model for multi-argument tools — better for production.
calculator: sandboxed eval
# Allowlist approach: only digits, operators, parens, dot, percent, whitespace
allowed = set("0123456789+-*/().% \t")
if not all(c in allowed for c in expression):
    raise ValueError(f"Unsafe expression: {expression}")

# eval with empty __builtins__ prevents access to any Python built-ins.
# Still: eval is inherently risky; for production replace with a proper
# expression parser (e.g. pyparsing, asteval, or sympy.sympify).
result = eval(expression, {"__builtins__": {}})
_rag_system global: lazy singleton pattern
_rag_system: RAGSystem | None = None

def _get_rag() -> RAGSystem:
    global _rag_system
    if _rag_system is None:
        _rag_system = RAGSystem()  # loads Chroma on first search_rag() call
    return _rag_system
Why a module-level global instead of passing RAGSystem as a dependency?

LangChain's Tool(func=...) binds a plain callable — there's no dependency injection point in the current abstraction. Proper alternatives: use a closure (make_search_tool(rag) returning a bound function), or use StructuredTool.from_function with an instance method. The global works fine in a single-process, single-threaded POC but is a problem if you ever fork workers — each process gets its own None copy and re-initialises Chroma independently.

MCP Server — Implementation Details
mcp_server.py · FastAPI · TOOL_REGISTRY
TOOL_REGISTRY design: dict of lambdas
TOOL_REGISTRY: Dict[str, Dict[str, Any]] = {
    "calculator": {
        "description": "...",
        "parameters": {"expression": "string"},
        "fn": lambda args: calculator(args.get("expression", "")),
    },
    # Each fn receives the raw `arguments` dict from the HTTP request body
    # and is responsible for extracting its own keys with safe defaults.
    "write_file": {
        "fn": lambda args: write_file(
            f"{args.get('file_path','')}|||{args.get('content','')}"
        ),
    },
}
Why this registry pattern rather than FastAPI route-per-tool?

A registry dict allows runtime introspection for GET /tools without duplicating metadata, and the POST /call dispatch is a single TOOL_REGISTRY[tool_name]["fn"](arguments) call rather than a large if/elif chain or dynamic route generation. Adding a new tool is a one-liner dict entry — no new route, no decorator. The trade-off: error messages are less specific because all tool failures surface through the same execute_tool catch block.

Pydantic v2 model shape
class ToolCall(BaseModel):
    tool_name: str
    arguments: Dict[str, Any] = {}      # default empty dict — GET /health never needs args

class ToolResult(BaseModel):
    tool_name: str
    result: str                          # always coerced to str via str(result) in execute_tool
    success: bool

class BatchResult(BaseModel):
    results: List[ToolResult]
    count: int                           # redundant with len(results) but convenient for callers
POST /batch: sequential, not concurrent
results = [execute_tool(req.tool_name, req.arguments) for req in requests]
# Sequential list comprehension — no asyncio.gather, no ThreadPoolExecutor.
# Intentional for a POC: tools aren't thread-safe (write_file has no locking,
# search_rag shares the global _rag_system).
# For concurrent batch execution: make tools async or wrap in executor,
# ensure Chroma's vectorstore.search is called from a single thread.
Error isolation strategy
def execute_tool(tool_name, arguments):
    if tool_name not in TOOL_REGISTRY:
        # Known-bad: surfaces as 404 on /call, as failed ToolResult on /batch
        return ToolResult(tool_name=tool_name, result=f"Unknown tool", success=False)
    try:
        result = TOOL_REGISTRY[tool_name]["fn"](arguments)
        return ToolResult(..., success=True)
    except Exception as exc:
        # Catch-all: prevents any tool exception from crashing the server.
        # /call returns HTTP 200 with success=false (not 500) for tool errors.
        # This is debatable — a 500 would be more REST-conventional for errors.
        return ToolResult(..., result=f"Error: {exc}", success=False)
No authentication — deliberate POC scope
⚠ Security: No auth on any endpoint

The server binds to 0.0.0.0:8000, meaning it's accessible to any process on the local network — not just localhost. write_file accepts arbitrary paths, creating a trivial arbitrary file-write primitive for any caller. For production: bind to 127.0.0.1, add an API key header check via FastAPI dependency injection (Depends(verify_api_key)), and sandbox write_file to a configured allowed directory.

End-to-End Data Flow
From user input through the full stack for a search query.
1
stdin → agent.py REPL

input("\nYou: ") reads a line. Passed as {"input": user_str} to AgentExecutor.invoke().

2
AgentExecutor → PromptTemplate → Ollama

The executor formats the ReAct prompt with {tools}, {tool_names}, {input}, and {agent_scratchpad} (empty on iteration 1). Sends the completed string to Ollama(model="gemma4:e4b") via HTTP POST to http://localhost:11434/api/generate.

3
Ollama response → output parser

LangChain's ReActSingleInputOutputParser scans the raw text for the Action: / Action Input: markers. On success returns an AgentAction; on parse failure returns an AgentFinish with the raw text as output (because handle_parsing_errors=True).

4
AgentAction → tool dispatch

Executor looks up action.tool in its internal tool name→callable map (built from the TOOLS list). Calls tool.run(action.tool_input), which calls the raw Python function with the string argument.

5
search_rag → RAGSystem.search() → Chroma

_get_rag().search(query, k=3) calls vectorstore.similarity_search_with_score(query, k=3). Chroma embeds the query using the same HuggingFaceEmbeddings instance, computes L2 distances against stored vectors, returns top-3 (Document, float) tuples.

6
Observation appended to scratchpad

Tool output is formatted as \nObservation: {result}\nThought: and appended to agent_scratchpad. On next iteration, the full growing transcript is re-injected into the prompt. This is why context window size matters: each iteration grows the prompt by ~(tool output length + 50 tokens).

7
Final Answer → stdout

When the parser finds Final Answer:, execution returns AgentFinish. The executor returns {"input": ..., "output": final_answer_text}. The REPL prints result["output"].

Known Limitations & Extension Points
What to fix before taking this beyond a POC.
Limitation now
  • No conversation memory — each .invoke() is stateless; prior turns are lost.
  • write_file uses ||| delimiter hack; fragile if content contains that string.
  • Chroma .persist() deprecated in ≥ 0.5; migrate to PersistentClient.
  • Batch endpoint is synchronous — slow for large batches with I/O-heavy tools.
  • RAG uses L2 distance; no score threshold filter, so bad matches still return.
  • 0.0.0.0 bind + no auth = trivially exploitable write_file.
  • Global _rag_system is not thread-safe under multi-worker Uvicorn.
Extension Point next
  • Add ConversationBufferMemory to AgentExecutor for multi-turn sessions.
  • Replace Tool with StructuredTool.from_function + Pydantic args schema.
  • Migrate to chromadb.PersistentClient + cosine space for cleaner API.
  • Make /batch async with asyncio.gather + async tool wrappers.
  • Add score_threshold param to RAGSystem.search(); expose in API.
  • Add FastAPI Depends(verify_api_key) middleware + bind to 127.0.0.1.
  • Pass RAGSystem instance via FastAPI lifespan + app.state instead of global.
  • Add BM25 hybrid re-ranking on top of dense retrieval for keyword-heavy queries.
  • Swap gemma4:e4b for a larger model by changing OLLAMA_MODEL — no other changes.
